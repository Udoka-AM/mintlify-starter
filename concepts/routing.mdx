When you submit a payout, Corridor doesn't hard-code a path for each currency pair. Instead, a route planner searches a graph of venues, assets, and executable legs to find the cheapest valid sequence from your Tempo balance to your recipient's local currency. The planner is pure — no network I/O, fully deterministic — and the only place a route is ever decided.

## The route graph

Every node in the graph is a **position**: a combination of a venue and an asset held there. Every edge is a **leg** Corridor can execute, with an associated cost and the environments (testnet or mainnet) where it is available.

```ts
interface LegSpec {
  kind: "tempo.transfer" | "tempo.dexSwap" | "across.bridge" | "solana.transfer"
      | "partner.payout" | "near.swap" | "zcash.shieldedBatch";
  from: { venue: Venue; asset: Asset };
  to:   { venue: Venue; asset: Asset };
}
```

The available legs today:

| Leg kind | From → To | Environments |
|---|---|---|
| `tempo.dexSwap` | `tempo/USDC.e` → `tempo/pathUSD` | Both |
| `across.bridge` | `tempo/pathUSD` ⇄ `base/USDC` ⇄ `solana/USDC` | Mainnet only (Across has no Tempo testnet) |
| `bridge.simulated` | `tempo/pathUSD` ⇄ `solana/USDC` | Testnet fallback |
| `partner.collect` | `partner_fiat/{11 currencies}` → `solana/USDC` | Both |
| `partner.payout` | `solana/USDC` → `partner_fiat/{32 currencies}` | Both |
| `partner.payout` | `base/USDC` → `partner_fiat/{NGN, GHS, KES, TZS, ZAR}` | Both (partners that settle on Base, such as Paj) |
| `near.swap` | `base/USDC` → `zcash_ironwood/ZEC` | Mainnet (NEAR Intents has no Tempo market) |
| `near.swap` | `tempo/pathUSD` → `zcash_ironwood/ZEC` | Testnet |
| `zcash.shieldedBatch` | `zcash_ironwood/ZEC` → `zcash_ironwood/ZEC` | Both — appended to shielded payouts |

## Hub enforcement

Tempo is the settlement hub. The planner enforces this without exception:

- Any **payout** that is not funded from the Tempo hub is rejected.
- Any **collection** that does not land on the Tempo hub is rejected.

This means every flow — regardless of source currency, destination currency, or privacy requirement — settles, holds, reconciles, and is visible to your treasury in one place.

<Note>
Hub enforcement is tested in `routing.test.ts`. It is not advisory — the planner returns an error if you attempt to route around it.
</Note>

## Planning steps

<Steps>
  <Step title="Validate">
    Payouts must be funded from the hub. Collections must land on it and are always public. A shielded payout must end in a shielded venue (`zcash_ironwood`); a public payout must not.
  </Step>
  <Step title="Search">
    The planner finds the cheapest path over the edges available in the requested environment. The batch leg is excluded from search and appended explicitly at the end.
  </Step>
  <Step title="Bracket">
    Payouts start with a `ledger.reserve` step that moves the amount into the customer's hold. Collections end with a `ledger.credit` that credits the customer's hub balance. Shielded payouts end with `zcash.shieldedBatch`.
  </Step>
  <Step title="Scope references">
    Each step receives a reference scope (payout, batch, or batch item), so a shielded batch uses one batch reference on the funding legs and a distinct item reference per recipient output.
  </Step>
</Steps>

## Route examples

```ts
// Public EUR → NGN payout
planRoute({
  corridor: "EUR-NGN",
  purpose: "payout",
  privacy: "public",
  source:      { venue: "tempo",        asset: "pathUSD" },
  destination: { venue: "partner_fiat", asset: "NGN" },
  env: "mainnet",
});
// → ledger.reserve
//   → across.bridge (tempo → base)
//   → partner.payout (base → NGN)

// Shielded supplier / payroll batch
planRoute({
  corridor: "USD-ZEC",
  purpose: "payout",
  privacy: "shielded",
  source:      { venue: "tempo",          asset: "pathUSD" },
  destination: { venue: "zcash_ironwood", asset: "ZEC" },
  env: "mainnet",
});
// → ledger.reserve
//   → across.bridge (tempo → base)
//   → near.swap (base USDC → ZEC)
//   → zcash.shieldedBatch
```

Resolved routes across environments:

| Flow | Testnet | Mainnet |
|---|---|---|
| EUR → NGN payout | reserve → bridge.simulated → partner.payout | reserve → across (Tempo→Base) → partner.payout (Base) |
| NGN → CNY payout | reserve → bridge.simulated → partner.payout | reserve → across (Tempo→Base) → across (Base→Solana) → partner.payout |
| NGN collection | partner.collect → bridge.simulated → ledger.credit | partner.collect → across (Solana→Base) → across (Base→Tempo) → ledger.credit |
| Shielded supplier batch | reserve → near.swap → zcash.shieldedBatch | reserve → across (Tempo→Base) → near.swap → zcash.shieldedBatch |

<Note>
The naira payout is **one bridge hop** on mainnet because Paj settles on Base. Currencies whose partners settle on Solana take two hops through Base, because Across has no direct Tempo ↔ Solana route.
</Note>

## Privacy is a path constraint, not a separate system

`privacy: "shielded"` is a constraint the planner enforces on the path: the final leg must end in the `zcash_ironwood` venue. It is not a separate subsystem or a different API. The same planner, the same saga engine, and the same ledger serve both public and shielded lanes. The only difference is which legs appear in the resolved route.

## N integrations, not N×N corridors

Because every flow passes through the Tempo hub, adding a new region means adding one ramp partner — not a new integration for every existing corridor. A Nigerian importer can reach a supplier in any currency Corridor's partners support, without Corridor building a dedicated NGN–CNY path.

A cross-border flow is always a collection followed by a payout, settled and reconciled at the hub in between.
